ภาพรวม 1 หน้าจอ

กติกาที่ทำให้ flow นี้ไม่พัง

1. ไม่มีอะไรข้าม Gate ❷ ได้ — ทุกความต้องการต้องผ่าน Product Alignment ให้ PO ตัดสินก่อนว่าจะเข้า Core / ทำเป็น Config / หรือแยกรายไซต์ ถ้าลัดเข้า Dev ตรง ๆ จะได้โค้ดเฉพาะไซต์ที่อีกไซต์ใช้ไม่ได้ ซึ่งขัดเป้าหมายที่จะให้ DTMU เป็น Product กลาง
2. ทุกขั้นต้องมี Work Product ที่เปิดดูได้ — ถ้าขั้นไหนจบแล้วไม่มีไฟล์/การ์ด/เอกสารเพิ่มขึ้นมา แปลว่าขั้นนั้นยังไม่จบ ใช้ตาราง “ของที่ได้จริงในแต่ละขั้น” เป็นตัวเช็ก
3. ทุกอย่างสาวกลับไปหาต้นทางได้ — Jira card → Topic ID (PA-xx-xx) → แถวใน Summary Gap → ชีตบันทึกดิบของ workshop เวลาลูกค้าถามว่า “ทำไมทำแบบนี้” ต้องเปิดย้อนได้ภายใน 1 นาที

Fit Gap Workshop — เก็บ Requirement

BA นำห้องPOImp / PCผู้ใช้ รพ.
1 รอบ = ครึ่งวัน–เต็มวัน

Input

  • Template รายโมดูล
  • ระบบ DTMU สำหรับเดินให้ดูจริง
  • ฟอร์ม/เอกสารที่ รพ. ใช้อยู่เดิม

สิ่งที่ทำ

  • เดิน flow หน้างานจริงทีละขั้น แล้วเทียบกับ DTMU ตรงหน้า
  • จดความต้องการดิบตามคำพูดผู้ใช้ ไม่ต้องรีบแปลง
  • สิ่งที่ยังตอบไม่ได้ให้ปักเป็น Question ?? พร้อมชื่อคนที่ต้องตอบ
  • เก็บหลักฐาน: ฟอร์มเดิม รูปหน้างาน ตัวอย่างรายงาน

Work Product

  • ชีตบันทึกดิบรายโมดูลใน Fitgap & Workshop.xlsx
  • รายการคำถามค้าง + เจ้าของคำถาม
  • ไฟล์แนบ/รูป/ฟอร์มเดิม
จบเมื่อ: เดินครบทุกหัวข้อของโมดูล · ทุกข้อมีวันที่ + ชื่อผู้ให้ข้อมูล · คำถามค้างทุกข้อมีคนรับไปตอบ
①b

BA เรียบเรียง + วิเคราะห์ — ทำบันทึกดิบให้กลายเป็นข้อที่ “จับคู่ได้”

BA เจ้าของโมดูล · Imp / PC ช่วยทาน · ผู้ใช้ ตอบคำถามค้าง
~3–5 วันหลัง workshop

Input

  • บันทึกดิบจากห้อง workshop
  • ฟอร์ม/รายงานเดิมที่เก็บมา
  • คำถามค้าง (Question ??)

สิ่งที่ทำ

  • แตกข้อ — 1 ย่อหน้าที่ผู้ใช้พูดมักมี 2–3 ความต้องการปนกัน ต้องแยกให้ 1 ข้อ = 1 เรื่อง ถ้าไม่แตก PO จับคู่ไม่ได้
  • เขียนใหม่ให้เป็นภาษากลาง — เปลี่ยนจากคำพูดผู้ใช้เป็น “ระบบต้องสามารถ…” ตัดคำเฉพาะไซต์ออก (เมืองสมุทรเขียน “เคสด่วน” · วลัยลักษณ์เขียน “คิวด่วน pass คิวอื่นได้” = เรื่องเดียวกัน)
  • หาปัญหาที่อยู่เบื้องหลัง — ผู้ใช้มักขอวิธีแก้มา ไม่ได้ขอปัญหา BA ต้องถอยกลับไปหาปัญหาจริง เพราะการจับคู่ข้ามไซต์เกิดที่ระดับปัญหา ไม่ใช่ระดับวิธีแก้
  • จัดโมดูลใหม่ (retag) — บางข้อถูกพูดในโมดูลหนึ่งแต่เป็นเรื่องของอีกโมดูล ต้องย้ายไปโมดูลจริง (“ระยะเวลารอคอย” ถูกพูดในงานพยาบาลของเมืองสมุทร แต่เป็นเรื่องของโมดูลคิว)
  • ตัดซ้ำ + รวมข้อภายในไซต์เดียวกันก่อน ลดจำนวนข้อที่ PO ต้องไล่
  • ปิดคำถามค้าง — ตามคำตอบจากผู้ใช้ให้จบ ไม่ส่งของที่ยังไม่รู้ต่อไป

Work Product

  • รายการ requirement ที่แตกเป็นข้อ เขียนเป็นภาษากลาง และติดโมดูลถูกต้องแล้ว
  • บันทึกปัญหาเบื้องหลังของแต่ละข้อ (ใช้จับคู่ในขั้น 2.5)
  • คำถามค้างที่ได้คำตอบแล้ว
จบเมื่อ: ทุกข้อเป็น 1 เรื่องเดียว อ่านแล้วรู้ว่า “ระบบต้องทำอะไรได้” โดยไม่ต้องกลับไปอ่านบันทึกดิบ · อยู่ในโมดูลที่ถูกต้อง · คำถามค้างปิดหมดหรือมีกำหนดตอบชัด
ทำไมขั้น ①b ขาดไม่ได้: ขั้นนี้คือขั้นที่ทำให้ requirement ของ 2 ไซต์ “พูดภาษาเดียวกัน” — ถ้าข้ามไป PO จะจับคู่เจอเฉพาะข้อที่บังเอิญใช้คำเหมือนกัน
หลักฐานจากของจริง: ตอนทำ Product-Alignment-2Site.xlsx รอบแรก จับคู่ข้ามไซต์ได้ 21 จาก 461 ข้อ ส่วนหนึ่งเพราะข้อความยังเป็นคำพูดผู้ใช้ดิบ ๆ และหลายข้อยังอยู่ผิดโมดูล — ตัวเลขนี้ควรสูงขึ้นเมื่อ ①b ทำครบ

2.5

⭐ Product Alignment — PO จับคู่ 2 ไซต์ และตัดสินว่าอะไรเข้า Product กลาง — GATE ❷

PO ลงมือเอง · ร่วมกับ Product Owner ฝั่ง DTMU · BA นั่งด้วยเพื่อตอบคำถามรายข้อ
ต่อจาก ② ทันที

Input

  • Summary Gap ของทั้ง 2 ไซต์ ที่ผ่าน ①b มาแล้ว
  • AS-IS ของ DTMU ที่ยืนยันจากขั้น ②
  • ทิศทาง Product · ข้อจำกัดสัญญา · กำลังทีม

สิ่งที่ทำ

  • จับคู่ requirement ที่เป็นเรื่องเดียวกันข้ามไซต์ — จับที่ระดับปัญหา ไม่ใช่ระดับวิธีแก้ จึงจะเห็นคู่ที่ข้ามโมดูลด้วย
  • ออกแบบ Product TO-BE ที่ตอบได้ทั้ง 2 ไซต์ — ถ้าความต้องการสวนทางกัน ให้แก้ด้วย config ไม่ใช่แยกโค้ด
  • ตัดสิน: Core / Config รายไซต์ / Connector รายไซต์ / เฉพาะไซต์ / ไม่ทำ พร้อมเหตุผลทุกข้อ
  • ให้ Priority และเรียงลำดับเข้า Sprint
  • ข้อที่ข้อมูลยังไม่พอ → ตีกลับให้ BA ที่ขั้น ①b หรือส่งเข้า Open Questions — ไม่ปล่อยผ่านแบบคลุมเครือ

Work Product

  • Product-Alignment-2Site.xlsx ที่มี PO Decision + เหตุผล ครบ
  • Topic ID (PA-xx-xx) ใช้อ้างตลอดสายงาน
  • รายการ Open Questions สำหรับวาระประชุม
ผ่าน Gate ❷ เมื่อ: ทุกหัวข้อที่จะทำต่อมี Decision + เหตุผลบันทึกไว้ · ไม่มีข้อไหนตัดสินให้แยกรายไซต์โดยไม่มีเหตุผลเขียนกำกับ · ข้อที่ยังตัดสินไม่ได้ถูกย้ายเข้า Open Questions พร้อมกำหนดตอบ
เส้นแบ่งระหว่าง BA กับ PO: BA รับผิดชอบว่า “ข้อนี้คืออะไร และ DTMU วันนี้ทำได้แค่ไหน” (①b + ②) · PO รับผิดชอบว่า “ข้อนี้กับข้อนั้นเรื่องเดียวกันไหม และ Product ควรเป็นอย่างไร” (2.5)
สัญญาณส่งมอบงาน = ช่อง “AS-IS ยืนยันแล้ว?” ในไฟล์ Excel — ถ้ายังเป็น “ต้องยืนยันกับ DTMU” แปลว่าขั้น ② ยังไม่จบ ยังไม่ควรเรียกประชุม PO

ส่งมอบตามงวดงาน — Final Work Product

ตามสัญญาแต่ละไซต์

Input

  • Work Product ที่สะสมมาทุกขั้น
  • เงื่อนไขงวดงานในสัญญา

สิ่งที่ทำ

  • รวบรวมเอกสารตามที่งวดนั้นกำหนด
  • ส่งมอบ → ผู้ว่าจ้างตรวจรับ → ออกหนังสือรับรอง

Work Product สุดท้าย

  • วลัยลักษณ์: งวด 1 แผนพัฒนา · งวด 2 SRD+Workflow+API+DB Schema · งวด 3 UAT+Training+คู่มือ · งวด 4 Go-live
  • เมืองสมุทร: งวด 1 ลงนาม (20%) · งวด 2 ตรวจรับ Go-live ปากน้ำ (30%) · งวด 3 ครบ 9 จุดบริการ (50%)
จบเมื่อ: ได้หนังสือรับรองการตรวจรับงานของงวดนั้น

ลูปย้อนกลับ — เกิดขึ้นแน่ ต้องรู้ว่าย้อนไปตรงไหน

L1 · ข้อมูลจาก workshop ไม่พอ (พบตอน ②) → นัดเก็บรอบ 2 เฉพาะหัวข้อที่ขาด ไม่ต้องรื้อทั้งโมดูล · ในไฟล์ Fit Gap Plan จะเห็นเป็นรอบที่ 2 ของโมดูลเดิม
L2 · ผู้ใช้ไม่ยืนยันตอน ④ → กลับไปแก้ที่ ③ (Flow/BR/FR) · ถ้าสิ่งที่ผู้ใช้ขอเปลี่ยนกระทบว่า “เข้า Core หรือแยกไซต์” ต้องวนกลับ Gate ❷ ให้ PO ตัดสินใหม่ ห้ามให้ BA ตัดสินเอง
L3 · Test / UAT ไม่ผ่าน → การ์ดเดิน In Review → Reopen → REOPENED กลับเข้า Dev · ถ้าที่ไม่ผ่านคือ “เข้าใจ requirement ผิด” ไม่ใช่ bug ให้ตีกลับถึง ③ และบันทึกเหตุผลไว้ที่ Topic เดิม
L4 · Requirement ใหม่โผล่กลางทาง → เปิดการ์ด [Fit Gap][ใหม่] : แล้วเข้าคิวที่ Gate ❷ ก่อนเสมอ · ไม่แทรกเข้า Dev ตรง ๆ แม้จะดูเป็นงานเล็ก เพราะงานเล็กที่ทำเฉพาะไซต์คือต้นเหตุที่ทำให้ Product แตกเป็น 2 ชุด
