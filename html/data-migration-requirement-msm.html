1วัตถุประสงค์และขอบเขตของเอกสาร

วัตถุประสงค์: ระบุให้ชัดว่าข้อมูลใดต้องถูกโอนย้าย ย้อนหลังเท่าใด ภายใต้กฎธุรกิจใด และจะถือว่า "สำเร็จ" ด้วยเกณฑ์ใด เพื่อให้ทีมพัฒนานำไปจัดทำ Data Mapping (S2-05) และ Data Dictionary (S2-06) ได้โดยไม่ต้องตีความเอง และเพื่อให้โรงพยาบาลลงนามยืนยันขอบเขตก่อนเริ่มงานแปลงข้อมูลจริง

หัวข้อขอบเขต
อยู่ในขอบเขตเอกสารนี้ความต้องการเชิงข้อมูล (What) — ชุดข้อมูล, ช่วงเวลา, กฎการแปลง, กฎการรวมผู้ป่วยซ้ำ, เกณฑ์ยอมรับ, สิ่งที่ รพ. ต้องจัดหา
ไม่อยู่ในขอบเขตเอกสารนี้วิธีการ/เครื่องมือ ETL, ตารางเวลาซ้อม, Runbook Cut-over, แผน Rollback → อยู่ใน Migration Plan (S1-03)
ขอบเขตสถานที่ครบ 9 จุดบริการ — เมืองสมุทรปู่เจ้าฯ 6 จุด + เมืองสมุทรปากน้ำ (สมุทรเวชกิจ) 3 จุด รวมเข้าฐานข้อมูล HA.OS เดียว
ระบบต้นทางHosXP 3 แหล่ง/3 เวอร์ชัน — v4 · v3 · vPCU
ระบบปลายทางHA.OS (TBM_* master / TB_* ธุรกรรม)
💡 หลักการตั้งขอบเขต: "ถูกต้อง 100% สำหรับข้อมูลวิกฤต" มาก่อน "ครบทุกข้อมูล" — ข้อมูลที่ไม่จำเป็นต่อการรักษา/เบิกจ่ายต่อเนื่อง ให้พิจารณาไว้ใน Non-scope (ข้อ 5) แล้วเปิด HosXP เดิมแบบ read-only ทดแทน

🔴 เงื่อนไขบังคับ: การเปิด HosXP เดิมแบบ read-only เป็นข้อกำหนดที่โรงพยาบาลต้องจัดหา (เครื่อง/สิทธิ์/ผู้ดูแล) — หาก รพ. ไม่สามารถคงระบบเดิมไว้ได้ ต้องทบทวนขอบเขตข้อ 4 ใหม่ทั้งหมด เพราะแนวทางทดแทนข้างต้นจะใช้ไม่ได้

6.1 ความต้องการด้านความครบถ้วน (Completeness)

รหัสระดับความต้องการเกณฑ์ยืนยัน (Verification)
MIG-R-001MUSTผู้ป่วยทุกรายในทั้ง 3 แหล่งต้องปรากฏใน HA.OS อย่างน้อย 1 ระเบียน (ยกเว้นที่คัดออกตามกฎ Non-scope ข้อ 5)Count ต้นทาง (หลังหักที่คัดออก) = Count ปลายทาง
MIG-R-002MUSTประวัติแพ้ยาต้องถูกรวมจากทุกแหล่งแบบ union — ห้ามตกหล่นแม้รายการเดียวเทียบรายรายการ (record-by-record) = 100%
MIG-R-003MUSTนัดหมายที่มีวันนัด ≥ วัน Go-live ต้องถูกย้ายครบทุกรายการ พร้อมแพทย์/คลินิก/ช่วงเวลาเดิมเทียบรายรายการ = 100% + Key User สุ่มเปิดดูตารางนัด 5 คลินิก
MIG-R-004MUSTยาที่ใช้ต่อเนื่องของผู้ป่วยโรคเรื้อรังต้องปรากฏในหน้าจอสั่งยาของ HA.OS ได้ทันทีวันแรกที่เปิดใช้สุ่มผู้ป่วยโรคเรื้อรัง 100 ราย เปิดเทียบกับ HosXP
MIG-R-005MUSTทุก visit/admit ที่ย้ายมาต้องผูกกับผู้ป่วยที่มีอยู่จริง (ไม่มี orphan)Referential check: orphan = 0
MIG-R-006SHOULDผลแล็บที่ย้ายมาต้องแสดงกราฟแนวโน้มย้อนหลังได้ต่อเนื่องไม่ขาดช่วงสุ่ม 30 เคสที่มีผลต่อเนื่อง เปิดดูกราฟ

6.2 ความต้องการด้านความถูกต้อง (Accuracy)

รหัสระดับความต้องการเกณฑ์ยืนยัน
MIG-R-007MUSTวันที่ทุกฟิลด์ต้องแปลง พ.ศ. → ค.ศ. ถูกต้อง ไม่มีวันเกิดเพี้ยน 543 ปีตรวจช่วงวันเกิดที่เป็นไปได้ (อายุ 0–130 ปี) · นอกช่วง = 0 record
MIG-R-008MUSTชื่อ-สกุลภาษาไทยต้องไม่มีอักขระเพี้ยนจากปัญหา encoding (โดยเฉพาะแหล่ง v3)สุ่ม 500 ราย/แหล่ง + ตรวจ pattern อักขระผิดอัตโนมัติ
MIG-R-009MUSTสิทธิการรักษาต้อง map เป็นรหัสมาตรฐานปลายทางถูกต้อง และตรวจสอบสิทธิกับ สปสช. ได้ทดสอบตรวจสอบสิทธิจริง 50 ราย ครบทุกประเภทสิทธิ
MIG-R-010MUSTรหัสยาต้อง map เข้ากับ drug master ของ HA.OS (TMT/รหัส 24 หลัก) ครบทุกรายการที่ยังใช้งานรายการยา active ที่ map ไม่ได้ = 0 · รายการที่เลิกใช้ให้ทำบัญชียกเว้น
MIG-R-011MUSTรหัส ICD10/ICD9 ต้องตรวจผ่าน master ปลายทาง — รหัสที่ไม่ผ่านต้องมีรายงานและได้รับการตัดสินจาก Data Ownerรายการ flag ทั้งหมดต้องมีสถานะปิด (แก้/ยอมรับ) ก่อน Cut-over
MIG-R-012MUSTยอดลูกหนี้ค้างชำระรวมและยอดเคลมค้างส่งรวม ปลายทาง = ต้นทางผลต่าง = 0.00 บาท · ลงนามโดย หน.การเงิน
MIG-R-013SHOULDยอดคงเหลือคลังยา/เวชภัณฑ์ ณ cut-off ตรงกับการตรวจนับจริงของ รพ.ผลต่างไม่เกิน 0.5% ของมูลค่ารวม และมีคำอธิบายทุกรายการที่ต่าง

6.3 ความต้องการด้านการใช้งานต่อเนื่อง (Continuity)

รหัสระดับความต้องการเกณฑ์ยืนยัน
MIG-R-014MUSTผู้ป่วยเดิมต้องค้นเจอด้วย HN เดิม ที่เคยใช้ในทุกแหล่ง (รองรับ HN ทางเลือก/HN เก่า)ค้นด้วย HN เดิมจาก 3 แหล่ง แหล่งละ 50 ราย เจอครบ
MIG-R-015MUSTต้องส่งเบิก e-Claim (CSOPBIL) จากข้อมูลที่ย้ายแล้วได้สำเร็จ ผ่านการตรวจของ สปสช.ส่งไฟล์ทดสอบจริง 1 รอบ ผ่านการตรวจ (ไม่มี error ระดับ reject)
MIG-R-016MUSTต้องส่งออก 43 แฟ้มจาก HA.OS ได้ตามรอบปกติของ รพ. โดยไม่ขาดช่วงคาบเกี่ยว Cut-overทดสอบ export 1 รอบเดือน + ตรวจความครบของแฟ้ม
MIG-R-017MUSTเลข HN/VN/AN ที่ระบบใหม่ออกให้ต้องต่อเนื่องจากเลขสุดท้ายของระบบเดิม ไม่ชนกันตรวจ running number ก่อนเปิดใช้ + ทดสอบออกเลขใหม่ 20 ครั้ง
MIG-R-018SHOULDรายงานประจำที่ รพ. ใช้อยู่ต้องดึงข้อมูลย้อนหลังที่ย้ายมาได้ถูกต้องเทียบ 10 รายงานหลักกับผลจาก HosXP ช่วงเดียวกัน

6.4 ความต้องการด้านคุณภาพข้อมูลและการตรวจสอบย้อนกลับ (Quality & Traceability)

รหัสระดับความต้องการเกณฑ์ยืนยัน
MIG-R-019MUSTทุกระเบียนที่ย้ายมาต้องระบุแหล่งที่มาได้ (v4/v3/vPCU) และ key เดิมของต้นทางตรวจฟิลด์ source system + legacy key ต้องไม่ว่าง
MIG-R-020MUSTทุกกฎการแปลง/คัดออกต้องบันทึกเป็นลายลักษณ์อักษรและตรวจย้อนกลับได้ว่าใครอนุมัติทะเบียนกฎการแปลงครบทุกข้อ + ผู้อนุมัติกำกับ
MIG-R-021MUSTระเบียนที่ย้ายไม่สำเร็จต้องมีรายงาน error ระบุสาเหตุรายรายการ ไม่ใช่แค่จำนวนรวมError report ดาวน์โหลดได้ · ทุกบรรทัดมีสาเหตุ
MIG-R-022SHOULDต้องเก็บ snapshot ข้อมูลต้นทางที่ใช้ในรอบจริงไว้ตรวจสอบย้อนหลังมีสำเนา snapshot + checksum เก็บไว้อย่างน้อย 1 ปี

6.5 ความต้องการด้านสมรรถนะและเวลา (Performance)

รหัสระดับความต้องการเกณฑ์ยืนยัน
MIG-R-023MUSTการ Load รอบจริงทั้งหมดต้องเสร็จภายในหน้าต่าง Downtime ที่ตกลง (12 ชม.) รวมเวลา Reconciliationวัดเวลาจริงในรอบซ้อมที่ 3 ด้วยข้อมูลปริมาณเท่าจริง
MIG-R-024MUSTการ Extract จากระบบเดิมต้องไม่ทำให้ HosXP ที่ยังให้บริการอยู่ช้าลงจนกระทบผู้ป่วยทำนอกเวลาให้บริการ / อ่านจาก replica · เฝ้าดู response time ระหว่าง Extract
MIG-R-025SHOULDต้องรองรับการ Load ซ้ำเฉพาะบางโดเมน (re-run รายส่วน) โดยไม่ต้องเริ่มใหม่ทั้งหมดทดสอบ re-run 2 โดเมนในรอบซ้อมที่ 3

6.6 ความต้องการด้านความปลอดภัยและกฎหมาย

รหัสระดับความต้องการเกณฑ์ยืนยัน
MIG-R-026MUSTข้อมูลผู้ป่วยต้องอยู่ในเครือข่าย/เครื่องที่โรงพยาบาลอนุญาตเท่านั้น ห้ามนำออกนอกสถานที่โดยไม่ได้รับอนุมัติบันทึกอนุมัติการเข้าถึง + ทะเบียนเครื่องที่ใช้
MIG-R-027MUSTสภาพแวดล้อมทดสอบ/ซ้อมต้องปกปิดข้อมูลระบุตัวตน (masking) หรือควบคุมการเข้าถึงเทียบเท่า Productionตรวจ config สภาพแวดล้อมทดสอบก่อนรอบซ้อมแรก
MIG-R-028MUSTผู้เข้าถึงข้อมูลต้องลงนามข้อตกลงรักษาความลับ และมีบันทึกการเข้าถึง (access log)ทะเบียนผู้เข้าถึง + NDA ครบทุกคน
MIG-R-029MUSTสำเนาข้อมูลชั่วคราว (staging/dump) ต้องถูกลบอย่างปลอดภัยเมื่อจบงานใบรับรองการทำลายข้อมูล ลงนามโดย IT รพ.

6.7 ความต้องการด้านการยืนยันโดยผู้ใช้

รหัสระดับความต้องการเกณฑ์ยืนยัน
MIG-R-030MUSTKey User แต่ละโดเมนต้องสุ่มเปิดเวชระเบียนจริงเทียบกับระบบเดิม และลงนามรับรองใบรับรองรายโดเมนครบทุกโดเมนที่ระบุในข้อ 2
MIG-R-031MUSTเคสผู้ป่วยที่จับคู่ไม่ชัดเจนต้องผ่านการตัดสินโดยเจ้าหน้าที่เวชระเบียน ห้ามรวมอัตโนมัติคิว manual review ต้องปิดครบ 100% ก่อน Cut-over
MIG-R-032SHOULDต้องมีช่องทางแจ้งปัญหาข้อมูลหลัง Go-live พร้อมเวลาตอบสนองที่ตกลงกันช่องทาง + SLA ระบุใน Hypercare Plan

7กฎธุรกิจและกฎการแปลงข้อมูล (Business & Transformation Rules)

กฎทุกข้อต้องมีผู้อนุมัติฝั่งโรงพยาบาล และจะถูกนำไปใช้เป็นข้อกำหนดใน Data Mapping (S2-05)

รหัสเรื่องกฎผู้อนุมัติ
BR-01ปี พ.ศ. → ค.ศ.ลบ 543 จากทุกฟิลด์วันที่ที่ตรวจพบว่าเป็น พ.ศ. · ถ้าผลลัพธ์อยู่นอกช่วงที่เป็นไปได้ → flag ไม่แปลงอัตโนมัติPM + IT รพ.
BR-02เลขบัตรประชาชนตรวจ checksum 13 หลัก · ไม่ผ่าน → เก็บค่าเดิมไว้แต่ทำเครื่องหมาย "รอตรวจสอบ" และห้ามใช้เป็น key จับคู่หน.เวชระเบียน
BR-03ผู้ป่วยไม่มีบัตรประชาชน (ต่างด้าว/ทารก/ไม่ทราบชื่อ)จับคู่ด้วย ชื่อ-สกุล + วันเกิด + เพศ + HN · หากยังไม่ชัด → เข้าคิว manual reviewหน.เวชระเบียน
BR-04วันเกิดไม่สมบูรณ์กรณีมีเฉพาะปี ให้ใช้ 1 ม.ค. ของปีนั้น และทำเครื่องหมายว่าเป็นค่าประมาณหน.เวชระเบียน
BR-05สิทธิการรักษาmap เป็นรหัสมาตรฐานปลายทาง · สิทธิที่หมดอายุก่อน cut-off ไม่ย้าย · ผู้ป่วยไม่มีสิทธิ → ตั้งเป็น "ชำระเงินเอง"หน.ศูนย์เคลม
BR-06รหัสยาmap เข้า drug master ปลายทางด้วยรหัส TMT/24 หลัก · ยาที่เลิกใช้แล้วให้ย้ายเฉพาะเพื่ออ่านประวัติ ห้ามให้สั่งใหม่ได้หน.เภสัชกรรม
BR-07หน่วยผลแล็บmap หน่วยและค่าอ้างอิงตามตารางที่ห้องแล็บยืนยัน · หน่วยที่ map ไม่ได้ → flag ห้าม Loadหน.ห้องปฏิบัติการ
BR-08ผู้ป่วยเสียชีวิตย้ายข้อมูลตามปกติ แต่ตั้งสถานะให้ระบบไม่เปิดนัดหมาย/สั่งการรักษาใหม่ได้หน.เวชระเบียน
BR-09ข้อมูลซ้ำภายในแหล่งเดียวกันเก็บระเบียนที่ปรับปรุงล่าสุด · ระเบียนอื่นเก็บเป็นประวัติ ไม่ลบทิ้งData Owner รายโดเมน
BR-10ข้อมูลทดสอบ/ขยะคัดออกตามเงื่อนไขที่ตกลง (เช่น ชื่อที่ขึ้นต้นด้วย "ทดสอบ") · ต้องทำรายการแนบให้ รพ. ตรวจก่อนคัดออกจริงหน.เวชระเบียน + IT
BR-11HN ซ้ำข้ามจุดบริการคง HN เดิมของแหล่งหลัก (v4) เป็น HN ปัจจุบัน · HN จากแหล่งอื่นเก็บเป็น HN ทางเลือก ค้นหาได้หน.เวชระเบียน
BR-12เอกสารแนบ/สแกนย้ายเฉพาะที่เปิดอ่านได้จริงและไม่เสียหาย · ไฟล์เสียหายให้รายงานเป็นรายการIT รพ.

8กฎการรวมผู้ป่วยซ้ำ (Deduplication) และ Golden Record

เป็นความต้องการที่มีความเสี่ยงสูงสุด เพราะผลลัพธ์กระทบความปลอดภัยผู้ป่วยโดยตรง

8.1 ลำดับกฎการจับคู่

ลำดับเงื่อนไขจับคู่ผลการตัดสินหมายเหตุ
1เลขบัตรประชาชนตรงกัน (ผ่าน checksum)รวมอัตโนมัติความเชื่อมั่นสูงสุด
2ชื่อ + สกุล + วันเกิด + เพศ ตรงกันทั้งหมดรวมอัตโนมัติใช้เมื่อไม่มีเลขบัตร
3ชื่อ+สกุลคล้ายกันมาก + วันเกิดตรง + เพศตรงmanual reviewครอบคลุมกรณีสะกดต่างเล็กน้อย
4ชื่อ+สกุลตรง แต่วันเกิดต่างกันเล็กน้อยmanual reviewมักเป็นความผิดพลาดการบันทึก
5ไม่เข้าเงื่อนไขข้างต้นถือเป็นคนละคนสร้างระเบียนแยก
🔴 ข้อห้ามเด็ดขาด: ห้ามรวมผู้ป่วยอัตโนมัติในกรณีที่เข้าเงื่อนไขลำดับ 3–4 · เคสเหล่านี้ต้องให้เจ้าหน้าที่เวชระเบียนตัดสินทีละราย และคิวต้องปิดครบก่อน Cut-over (MIG-R-031)

8.2 กฎการสร้าง Golden Record

ประเภทข้อมูลวิธีเลือก/รวมเหตุผล
ชื่อ-สกุล, ที่อยู่, เบอร์ติดต่อใช้ค่าที่ปรับปรุงล่าสุดสะท้อนสถานะปัจจุบัน
เลขบัตรประชาชนใช้ค่าที่ผ่าน checksum · ถ้ามีหลายค่าที่ผ่าน → manual reviewป้องกันข้อมูลตัวตนผิด
ประวัติแพ้ยา วิกฤตรวมทุกแหล่ง (union) ห้ามตัดออก แม้ซ้ำก็เก็บทั้งคู่แล้วให้เภสัชตรวจภายหลังตกหล่น 1 รายการ = อันตรายถึงชีวิต
ประวัติการรักษา / visitรวมทุกแหล่ง เรียงตามเวลา คงแหล่งที่มาไว้ทุกระเบียนต้องเห็นประวัติต่อเนื่อง
HNHN แหล่งหลักเป็นหลัก · ที่เหลือเป็น HN ทางเลือก (BR-11)ผู้ป่วยยังถือบัตรเดิม
สิทธิการรักษาใช้สิทธิที่ active ล่าสุด ณ cut-offใช้เบิกจ่ายได้จริง
📊 ตัวอย่างผลที่คาดหมาย (จาก Profiling เบื้องต้น): จากผู้ป่วยรวม ~480,000 ราย คาดว่าเป็นคนซ้ำ ~85,000 ราย (ส่วนใหญ่ v4↔v3) เหลือผู้ป่วยจริง ~395,000 ราย โดยมีเคสที่ต้อง manual review ประมาณ 3,000–5,000 เคส → ต้องเผื่อกำลังคนเวชระเบียน 2 คน × 3 สัปดาห์ ในแผนงาน

ข้อมูลวิกฤต แพ้ยา · ยา active · ผล Lab · นัดหมาย100%เทียบรายรายการ ต้นทาง ↔ ปลายทางNo-Go — ห้ามเปิดใช้ระบบ
ข้อมูลการเงิน (ลูกหนี้ · เคลมค้าง)100% ของยอดรวมControl total + ลงนามโดย หน.การเงินNo-Go
ทะเบียนผู้ป่วย + สิทธิ100% ของจำนวนRecord count + สุ่มตรวจNo-Go
ประวัติการรักษา / Orders / ICD≥ 99.9%Record count รายโดเมน + error reportเปิดใช้ได้ ถ้ามีแผนแก้ที่ตกลงกัน
ใบเสร็จ / รายงานย้อนหลัง≥ 99.5%Count + สุ่มตรวจแก้ในช่วง Hypercare
เอกสารแนบ / สแกน≥ 95%Count ไฟล์ + สุ่มเปิดอ่านแก้ภายหลัง ไม่บล็อก Go-live
💡 เกณฑ์เหล่านี้จะถูกนำไปใช้เป็นเงื่อนไข Go/No-Go ในเอกสาร S2-14 (Reconciliation) และ S2-17 (Go-Live/Cutover Checklist) — ตัวเลขทุกช่องต้องได้รับการยืนยันจากคณะทำงาน HIS ก่อน

10ความต้องการด้าน Cut-off, Delta และ Downtime

หัวข้อค่าที่ต้องการหมายเหตุ
วิธีการโอนย้ายFull load + DeltaFull load ล่วงหน้า แล้วตาม Delta เฉพาะข้อมูลที่เปลี่ยนในคืน Cut-over เพื่อลด Downtime
วันตัดยอด Full loadก่อน Cut-over 7 วันให้เวลาตรวจสอบก่อนรอบจริง
ช่วง Delta ที่ต้องรองรับ7 วันสุดท้ายต้องระบุได้ว่าระเบียนใดเปลี่ยนแปลง (ใช้ timestamp ต้นทาง)
หน้าต่าง Downtime ที่ยอมรับได้ไม่เกิน 12 ชม.เลือกคืนวันหยุด · ต้องวัดเวลาจริงในรอบซ้อมที่ 3
Data freeze ระบบเดิม22:00 น. คืนก่อน Go-liveหลังเวลานี้ HosXP บันทึกใหม่ไม่ได้ · ใช้แบบฟอร์มมือระหว่าง freeze
การบันทึกย้อนหลังช่วง freezeคีย์เข้า HA.OS ภายใน 24 ชม.ต้องมีขั้นตอนและผู้รับผิดชอบชัดเจน
จุดตัดสินใจ Go/No-Goหลัง Reconciliation ข้อมูลวิกฤตครบตามเกณฑ์ข้อ 9 · ผู้ตัดสิน = คณะทำงาน HIS + PM
ระยะเปิด HosXP read-only2 ปี หลัง Go-liveเงื่อนไขรองรับ Non-scope (ข้อ 5)
⚠️ ข้อสังเกต: หากต้นทางบางตารางไม่มี timestamp การแก้ไขที่เชื่อถือได้ จะทำ Delta ไม่ได้ ต้อง Full load ทั้งหมดในคืน Cut-over ซึ่งจะทำให้ Downtime ยาวขึ้นมาก — ประเด็นนี้ต้องตรวจให้จบใน Data Profiling ก่อนยืนยันหน้าต่าง Downtime (ดูประเด็นค้าง OI-02)

11ความปลอดภัยข้อมูลและ PDPA

  • ข้อมูลผู้ป่วยทั้งหมดถือเป็นข้อมูลส่วนบุคคลอ่อนไหว — การเข้าถึงต้องมีเหตุผลตามหน้าที่และได้รับอนุมัติเป็นลายลักษณ์อักษร
  • สภาพแวดล้อมซ้อม/ทดสอบต้องปกปิดข้อมูลระบุตัวตน หรือควบคุมการเข้าถึงเทียบเท่า Production (MIG-R-027)
  • ห้ามคัดลอกข้อมูลออกนอกเครือข่ายที่โรงพยาบาลกำหนด · ห้ามใช้อุปกรณ์เก็บข้อมูลส่วนตัว
  • ผู้ปฏิบัติงานทุกคนต้องลงนามข้อตกลงรักษาความลับ และมีบันทึกการเข้าถึงย้อนหลังได้
  • สำเนาชั่วคราว (staging/dump/backup ระหว่างทาง) ต้องถูกลบอย่างปลอดภัยเมื่อจบงาน พร้อมใบรับรองการทำลาย (MIG-R-029)
  • การส่งข้อมูลระหว่างระบบต้องเข้ารหัสระหว่างทาง
💡 รายละเอียดมาตรการทั้งหมดอยู่ในเอกสารด้านความมั่นคงปลอดภัยของโครงการ — เอกสารฉบับนี้ระบุเฉพาะข้อกำหนดที่ผูกกับงานโอนย้ายข้อมูล

12สิ่งที่โรงพยาบาลต้องจัดหา (Input จาก รพ.)

รายการเหล่านี้เป็นเงื่อนไขเริ่มงาน — หากล่าช้าจะกระทบวันเริ่มซ้อมและวัน Go-live โดยตรง

#สิ่งที่ต้องจัดหาผู้รับผิดชอบ (รพ.)ต้องได้ภายในผลกระทบหากล่าช้า
1สิทธิ์เข้าถึง HosXP แบบ read-only ครบทั้ง 3 แหล่งหน.ITส.ค. 2569เริ่ม Profiling ไม่ได้
2สำเนาฐานข้อมูล (dump) สำหรับสภาพแวดล้อมซ้อมหน.ITก.ย. 2569ซ้อมรอบ 1 เลื่อน
3ยืนยันปีย้อนหลังทุกชุดข้อมูล (ข้อ 4)คณะทำงาน HISส.ค. 2569ทำ Mapping ไม่ได้
4ยืนยันรายการ Non-scope (ข้อ 5)คณะทำงาน HISส.ค. 2569เสี่ยงข้อพิพาทตอนตรวจรับ
5ตารางเทียบรหัสยา รพ. → TMT/24 หลักหน.เภสัชกรรมก.ย. 2569ยา map ไม่ได้ → สั่งยาไม่ได้วันเปิดใช้
6ตารางหน่วยและค่าอ้างอิงผลแล็บหน.ห้องปฏิบัติการก.ย. 2569ผลแล็บแสดงผิดหน่วย
7รายการค่าบริการ + ชุดราคาตามสิทธิที่ใช้จริงหน.การเงินก.ย. 2569คิดเงินผิดวันเปิดใช้
8กำลังคนเวชระเบียนสำหรับ manual review เคสซ้ำหน.เวชระเบียนต.ค.–พ.ย. 2569ปิดคิวไม่ทัน → No-Go
9Key User ลงนามรับรองผลรายโดเมนทุกรอบซ้อมData Owner ทุกโดเมนทุกรอบซ้อมไม่มีหลักฐานตรวจรับ
10ยืนยันหน้าต่าง Downtime + วันหยุดที่ใช้ Cut-overคณะทำงาน HISพ.ย. 2569วางแผน Cut-over ไม่ได้
11เครื่อง/พื้นที่จัดเก็บสำหรับ HosXP read-only หลัง Go-liveหน.ITธ.ค. 2569แนวทางทดแทน Non-scope ใช้ไม่ได้
12อนุมัติการเข้าถึงข้อมูลผู้ป่วยตาม PDPA + NDAผู้บริหาร รพ.ส.ค. 2569เข้าถึงข้อมูลจริงไม่ได้

13เกณฑ์การยอมรับเอกสารและงานโอนย้าย

13.1 เกณฑ์ยอมรับเอกสารฉบับนี้

  • ทุกช่องที่ไฮไลต์ไว้ถูกแทนที่ด้วยค่าจริงจาก Data Profiling และการยืนยันของโรงพยาบาลแล้ว
  • ทุกโดเมนข้อมูลมี Data Owner ที่ระบุชื่อได้ (ข้อ 2)
  • รายการ Non-scope (ข้อ 5) ได้รับการยืนยันเป็นลายลักษณ์อักษร
  • กฎการแปลงทุกข้อ (ข้อ 7) มีผู้อนุมัติกำกับ
  • ประเด็นค้างระดับสูง (ข้อ 14) ปิดครบหรือมีแผนปิดที่ตกลงกัน
  • ลงนามครบตามข้อ 15

13.2 เกณฑ์ยอมรับผลการโอนย้าย (ใช้ตอน Cut-over)

  • ความต้องการระดับ MUST ทุกข้อผ่านเกณฑ์ยืนยันที่ระบุไว้
  • ข้อมูลวิกฤตผ่าน Reconciliation 100% (ข้อ 9)
  • คิว manual review เคสผู้ป่วยซ้ำปิดครบ 100%
  • ไม่มีประเด็นระดับวิกฤต/สูงค้างอยู่
  • Key User ลงนามรับรองครบทุกโดเมน
  • ทดสอบส่งเบิก e-Claim ผ่านแล้วอย่างน้อย 1 รอบ
🔴 เงื่อนไข No-Go: หากข้อใดข้อหนึ่งใน 13.2 ไม่ผ่าน ให้ถือเป็น No-Go และดำเนินการตามแผน Rollback ใน Migration Plan (S1-03) ข้อ 10 โดยไม่ต้องรอการตัดสินใจเพิ่มเติม

14ข้อสมมติ ข้อจำกัด และประเด็นค้าง

14.1 ข้อสมมติ (Assumptions)

  • โรงพยาบาลคงระบบ HosXP เดิมไว้แบบ read-only ได้อย่างน้อย 2 ปี หลัง Go-live
  • โครงสร้างฐานข้อมูลต้นทางไม่มีการเปลี่ยนแปลงระหว่างโครงการ
  • ปริมาณข้อมูลเติบโตไม่เกิน 10% จากที่ประเมินไว้ ณ วันจัดทำเอกสาร
  • โรงพยาบาลจัดกำลังคนสำหรับตรวจสอบและ manual review ได้ตามข้อ 12

14.2 ประเด็นค้าง (Open Issues)

รหัสประเด็นระดับผู้รับผิดชอบต้องปิดภายใน
OI-01ยังไม่ยืนยันปีย้อนหลังของผล Lab (3 ปี หรือ 5 ปี) — กระทบปริมาณข้อมูลอย่างมีนัยสำคัญสูงองค์กรแพทย์ + PMก.ย. 2569
OI-02ตารางบางส่วนใน v3 ไม่มี timestamp การแก้ไข → อาจทำ Delta ไม่ได้ ต้อง Full load ในคืน Cut-overสูงSenior Imp เตทีมต.ค. 2569
OI-03ยังไม่ได้ตารางเทียบรหัสยา รพ. → TMT ครบทุกรายการสูงหน.เภสัชกรรมก.ย. 2569
OI-04พื้นที่จัดเก็บเอกสารสแกน ~1.2 TB ยังไม่ยืนยันว่าเพียงพอ (กระทบข้อ 4 รายการ 18)กลางหน.IT รพ.ต.ค. 2569
OI-05เกณฑ์คัดข้อมูลทดสอบ/ขยะ (BR-10) ยังไม่ได้รับการยืนยันเป็นลายลักษณ์อักษรกลางหน.เวชระเบียนก.ย. 2569
OI-06ยังไม่ระบุ Data Owner ของข้อมูลรังสี/PACSกลางคณะทำงาน HISก.ย. 2569
⚠️ กติกา: ประเด็นระดับ "สูง" ที่ยังไม่ปิด จะทำให้ยังไม่สามารถอนุมัติ Data Mapping (S2-05) ได้ เพราะขอบเขตยังไม่นิ่ง
